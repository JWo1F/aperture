The user has explicitly asked: commit after every completed feature
without being prompted. Don't accumulate multi-feature batches.

## When to commit

After all three of these are true:
1. The change is a complete, coherent unit (one feature or one fix).
2. `flutter analyze` passes (see the `verify-changes` skill).
3. `flutter test` + `flutter build macos --debug` pass.

Don't wait for the user to say "commit". Commit as soon as the above
holds. The user will say if they want to amend.

## Commit message rules

- **No AI attribution.** No `Co-Authored-By: Claude`, no "generated by",
  no AI-related trailers. The user has rejected these and will reject
  them again.
- Subject under ~70 chars, imperative mood ("Add foo", "Fix bar baz",
  "Rework toolbar").
- Body wrapped at ~70 cols, explains the **why** + non-obvious choices.
  Skip the *what* — the diff already shows it.
- Group related sub-bullets with a leading verb line. Use a HEREDOC so
  formatting is preserved:

```bash
git commit -m "$(cat <<'EOF'
Subject line under ~70 chars

Paragraph explaining the reason for the change, the trade-offs you
considered, and any non-obvious choices. Avoid restating the diff.

- Specific point one (with rationale, not just description)
- Specific point two
- ...
EOF
)"
```

## Staging

Be explicit — `git add <files>` listing exactly the paths that belong to
this feature. Don't `git add .` or `git add -A` (they pick up
`.vscode/`, OS files, etc.).

## Verification after commit

After `git commit`, sanity-check with `git log --oneline | head -5` so
you confirm the commit went in. Don't push unless explicitly asked.
